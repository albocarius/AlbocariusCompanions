## Q1 — Wanderer spawning

Status: VERIFIED

### Answer
**Behavior.** Wanderers are spawned by the TaleWorlds behavior `CompanionsCampaignBehavior` (namespace `TaleWorlds.CampaignSystem.CampaignBehaviors`), which the sandbox campaign registers via `SandBoxManager.Initialize`. It is the only behavior in all decompiled sources that mass-spawns wanderer heroes; SandBox issue behaviors only borrow wanderer templates to create quest NPCs (e.g. the "notable wants his daughter found" issue creates one daughter hero from a random wanderer template).

**When it runs.** `RegisterEvents` subscribes to `OnNewGameCreatedEvent`, `OnGameLoadFinishedEvent`, `DailyTickEvent`, `WeeklyTickEvent`, `HeroCreated`, `HeroKilledEvent` and `HeroOccupationChangedEvent`:

- New game (`OnNewGameCreated`): builds the wanderer-template catalog, shuffles `Town.AllTowns` and creates one wanderer per town in a loop whose index stays below the target — i.e. about 0.6 wanderers per town exist at game start.
- Daily (`DailyTick`), in order: `TryKillCompanion` (10 % chance per day: picks a random template from `_aliveCompanionTemplates`, finds the first alive wanderer hero with that `Template`, and removes it via `KillCharacterAction.ApplyByRemove` if it is not hired (`CompanionOf == null`) and not in the player's current settlement), then `SwapCompanions` (moves unrecruited wanderers between random towns — placement only, count unchanged), then `TrySpawnNewCompanion` (at most one new wanderer per day).
- Weekly (`WeeklyTick`): cleanup only — dead/disabled wanderers whose `DeathDay` is ≥ 40 days old (`RemoveWandererAfterDays`) are unregistered via `CampaignObjectManager.UnregisterDeadHero`. No spawning.
- Game load (`OnGameLoadFinished`): rebuilds the alive-wanderer bookkeeping only, never spawns. (A second method `OnGameLoaded(CampaignGameStarter)` with the same body exists but is not subscribed in `RegisterEvents` — dead code.)

**How the number is decided.** The target is derived from towns, not a fixed number: `_desiredTotalCompanionCount` = `Town.AllTowns.Count` × 0.6 (`DesiredCompanionPerTown` = 0.6). A daily spawn happens only when the current count is below that target, and creates at most one hero per day. The destination town is chosen by predicate: not the player's current settlement, no `SiegeEvent`, and no already-unrecruited wanderer in `Settlement.HeroesWithoutParty` (so at most one hireable wanderer per town). `GetCompanionTemplateTypeToSpawn` picks the skill category (Combat, Scouting, Tactics, … each with a fixed weight such as 5/38) whose share of the target is furthest below its weight; `GetCompanionTemplateToSpawn` then shuffles that category and returns the first template that has no living hero. The hero is created with `HeroCreator.CreateSpecialHero(template, townOfTemplateCulture, null, null, age)` (age = coming-of-age + 5 + random 0–11), equipment is re-rolled with the `companion_armor`/`companion_weapon`/`companion_horse` item modifiers (`AdjustEquipments`), and `EnterSettlementAction.ApplyForCharacterOnly` moves the hero into the destination town. The catalog itself is every loaded `CharacterObject` with `IsTemplate` and `Occupation == Occupation.Wanderer` (`InitializeCompanionTemplateList`).

**Exactly where and how existing wanderers are counted.** The spawn decision never counts heroes ad hoc: the behavior maintains a `HashSet` field `_aliveCompanionTemplates` of wanderer *templates* (unique `CharacterObject`s) that currently have a living hero. The exact check is in `TrySpawnNewCompanion`: `_aliveCompanionTemplates.Count < _desiredTotalCompanionCount`. Per-category counting in `GetCompanionTemplateTypeToSpawn` loops the category's templates and tests `_aliveCompanionTemplates.Contains(item)`. On a new game the set is filled only through `OnHeroCreated` as each wanderer is created; on load it is rebuilt by iterating `Hero.AllAliveHeroes` (plus still-alive entries of `Hero.DeadOrDisabledHeroes`) filtered on `IsWanderer` (`OnGameLoadFinished`); it is then maintained by `OnHeroCreated` (adds living wanderers, bypassing the known-template check), `OnHeroKilled` (removes the template; if the dead wanderer was never `HasMet` the hero is immediately unregistered with `CampaignObjectManager.UnregisterDeadHero`) and `OnHeroOccupationChanged` (add/remove when a hero becomes or stops being a wanderer). Except on creation, only templates present in the wanderer catalog are counted (`IsTemplateKnown`). Because counting is per template, vanilla keeps roughly one hero per wanderer template and the population oscillates around the 0.6-per-town target via the daily kill/spawn churn. A "wanderer" here is any hero with `Occupation == Occupation.Wanderer` (`Hero.IsWanderer`); the full classification is Q2.

**Implications for the mod (orchestrator note).** `_aliveCompanionTemplates` drives three things: the spawn target check, template choice, and the daily kill (`TryKillCompanion`). A mod companion created alive with `Occupation.Wanderer` is added by `OnHeroCreated` (template gate bypassed), so it would (a) count toward the target and (b) be eligible for random removal while unhired. Keeping mod companions' templates out of this set (see Q10) solves both. `SwapCompanions` selects by `IsWanderer && CompanionOf == null` directly from settlements, not from the set, so mod companions still get vanilla tavern movement.

## Q2 — Which heroes count as wanderers

Status: VERIFIED

### Answer

**Short answer.** A hero is a wanderer iff its `Occupation` is `Occupation.Wanderer` — that is the whole test (`Hero.IsWanderer => Occupation == Occupation.Wanderer`). There is no wanderer flag, no tag list and no "hired" flag involved in the definition. But the *count* from Q1 (`_aliveCompanionTemplates.Count`, compared with `Town.AllTowns.Count * 0.6f`) is **not a hero count**: it is a `HashSet<CharacterObject>` of hero **templates**, so several living heroes that were made from the same character template occupy exactly **one** slot, and one hero dying (or changing occupation) frees that slot even if other heroes from the same template are still alive.

**Occupation (the only criterion).** A hero's occupation is copied from its character template at creation (`Hero.SetInitialValuesFromCharacter` assigns `Occupation = CharacterObject.GetDefaultOccupation()`), and the template's occupation comes straight from the `occupation` attribute of the character XML (`CharacterObject.Deserialize`). After creation the only way to become or stop being a wanderer is `Hero.SetNewOccupation`, which raises `HeroOccupationChangedEvent`; `CompanionsCampaignBehavior.OnHeroOccupationChanged` removes the hero from the count when the old occupation was `Wanderer` and adds it when the new one is. So the set follows occupation, always, in both directions.

**Flags.** The only other flag the counting code ever looks at is `CharacterObject.IsTemplate`, and only to build the "known wanderer template" catalog (`InitializeCompanionTemplateList` = every registered `CharacterObject` with `IsTemplate && Occupation == Occupation.Wanderer`, from `MBObjectManager.GetObjectTypeList<CharacterObject>()`). Nothing else qualifies: `Hero.CompanionOf` is hire state, not identity; `Hero.IsSpecial` is a different occupation; `CharacterObject.HiddenInEncyclopedia` is display-only. The game defines "wanderer template" the same way in a second, independent place (`CharacterHelper.GetRandomCompanionTemplateWithPredicate` uses the identical predicate), and the conversation layer classifies by the same hero property (`WandererTag.IsApplicableTo => HeroObject.IsWanderer`) — so there is no second notion of wanderer anywhere.

**Who is added / removed.**
- New game / save load: `OnGameLoadFinished` walks `Hero.AllAliveHeroes` and adds `hero.Template` for every `IsWanderer` hero, then walks `Hero.DeadOrDisabledHeroes` and adds those with `IsAlive && IsWanderer`. Both go through `AddToAliveCompanions`, whose `IsTemplateKnown` gate is skipped only on the creation path.
- Runtime: `OnHeroCreated` adds the hero when `hero.IsAlive && hero.IsWanderer` (gate bypassed via `isTemplateControlled: true`); `OnHeroOccupationChanged` moves it in/out; `OnHeroKilled` calls `RemoveFromAliveCompanions(victim)` **for every killed hero, with no occupation guard** — so a non-wanderer hero that happens to share a wanderer template also frees the slot.
- The set is never saved (`SyncData` is empty), it is rebuilt from the hero rosters on every load. Anything a mod does to wanderer identity must therefore be visible to those same filters at load time, not only at runtime.

**Hired vs unhired: irrelevant to the count.** Hiring is `AddCompanionAction.ApplyInternal` → `companion.CompanionOf = clan` (plus `AddHeroToPartyAction` in the dialog consequence) and never touches `Occupation`, so a hired companion keeps `IsWanderer` and its template keeps holding a slot. Firing (`RemoveCompanionAction.ApplyInternal`) makes the hero fugitive and resets equipment but keeps `Occupation.Wanderer`, so ex-companions keep counting too. Hire state appears only in the *downstream* filters, never in the count itself: the daily cull requires the picked hero to have `CompanionOf == null` and a settlement different from the player's (if the first alive hero of that template is hired, the cull just does not happen that day); `SwapCompanions` moves only `IsWanderer && CompanionOf == null` heroes taken from `Settlement.HeroesWithoutParty`; and the spawn predicate treats a town as "already has a wanderer" only for unhired ones (`!y.IsWanderer || y.CompanionOf != null`). Separately, the player's own companion cap (`too_many_companions()` → `Clan.PlayerClan.Companions.Count >= Clan.PlayerClan.CompanionLimit`) is an unrelated number and is not part of this count.

**Alive.** "Alive" here means membership in `Hero.AllAliveHeroes` (= `CampaignObjectManager`'s alive roster). A hero is in that roster unless its `HeroState` is `Dead` or `Disabled` (`CampaignObjectManager.OnHeroAdded` / `HeroStateChanged` shuffle heroes between the two lists), so `NotSpawned`, `Active`, `Fugitive`, `Prisoner`, `Released` and `Traveling` wanderers are all counted. Consequences: a wanderer is counted from the moment it is created (`CreateSpecialHero` fires `OnHeroCreated` while the hero is still `NotSpawned`); a fired, fugitive companion is still counted; a wanderer removed by the cull leaves both lists (`KillCharacterAction.MakeDead` sets `CharacterStates.Dead` before `HeroKilledEvent` fires) and can never come back, because dead wanderers are unregistered from the campaign entirely (`OnHeroKilled` for never-met ones, `WeeklyTick` after 40 days, via `CampaignObjectManager.UnregisterDeadHero`). Note `Hero.IsAlive` is literally `!IsDead`, which is why the load pass also scans `DeadOrDisabledHeroes` for `IsAlive && IsWanderer` — a `Disabled` hero would be counted there; in the decompiled code the only callers of `DisableHeroAction.Apply` are StoryMode scripted-hero cleanups, so in sandbox the practical ways out of the count are dying and changing occupation.

**Not checked anywhere:** age/child, clan (the player's clan, an AI lord's hired companions travelling in a party — all counted), culture, gender, `HasMet` (only affects how fast a dead wanderer is unregistered), settlement or party membership, and whether the hero is reachable/visible in the encyclopedia.

**Consequence for the mod.** Any alive hero whose `Occupation` is `Wanderer` is indistinguishable from a vanilla named companion to this logic — even one created for a quest. The "notable wants his daughter found" quest creates the daughter with `HeroCreator.CreateSpecialHero` from a template fetched by `GetRandomCompanionTemplateWithPredicate`, and hero initialization keeps the template's occupation unless the caller overrides it (`HeroCreator.InitializeHeroFromSettings`), so she is `IsWanderer`: she consumes a wanderer slot and is eligible for the daily cull because `CompanionOf` is null. A mod companion with `Occupation.Wanderer` behaves the same way unless it is excluded (Q10).

**Orchestrator note (verified).** `Hero.Template` is `CharacterObject.OriginalCharacter`, i.e. the private `_originCharacter`; it is null when the hero's `CharacterObject` was not derived from another character (`IsOriginalCharacter`). Heroes made by `HeroCreator.CreateSpecialHero` from a template are derived, so `Template` is that template object — this is the key the wanderer set uses and the natural key for excluding mod companions (Q10).

## Q3 — Tavern placement and movement

Status: VERIFIED

### Answer
**The placement state itself.** A hero's settlement presence without a party is one property: `Hero.StayingInSettlement`. Its setter is the whole bookkeeping — it removes the hero from the old settlement's hero-without-party cache (`Settlement.RemoveHeroWithoutParty`) and adds it to the new one (`Settlement.AddHeroWithoutParty`), which is what `Settlement.HeroesWithoutParty` exposes. `Hero.CurrentSettlement` falls back to it only when the hero belongs to no party and no prisoner party. Exactly one write in the decompiled sources sets it non-null: `EnterSettlementAction.ApplyForCharacterOnly(hero, settlement)`; it is cleared by `LeaveSettlementAction.ApplyForCharacterOnly(hero)`, by joining a party (`AddHeroToPartyAction` sets it to null, as does the internal `Hero.OnAddedToParty`), and by capture/disable paths (`TakePrisonerAction`, `KillCharacterAction`, `DisableHeroAction`, `EndCaptivityAction`). So "which settlement a wanderer is in" is not a coordinate or a party — it is this one reference, maintained by two action APIs.

**Initial placement.** Every wanderer the game spawns ends up in a town through `CompanionsCampaignBehavior`: at new game one per (shuffled) town, daily at most one more (`CreateCompanionAndAddToSettlement`). That method creates the hero with `HeroCreator.CreateSpecialHero(template, cultureMatchedRandomTown, null, null, age)` — the culture-matched town is only the hero's `BornSettlement`, creation does not place the hero anywhere — then `hero.ChangeState(Hero.CharacterStates.Active)` and finally `EnterSettlementAction.ApplyForCharacterOnly(hero, settlement)` puts the hero into the caller-chosen town (daily spawns pick a random town that is not the player's current settlement, has no `SiegeEvent`, and has no still-unhired wanderer in `HeroesWithoutParty`).

**Movement between settlements over time.** One mechanic, one cadence: `CompanionsCampaignBehavior.SwapCompanions`, called from `DailyTick` after `TryKillCompanion` and before `TrySpawnNewCompanion`. It splits `Town.AllTowns` into two halves by index; it takes one random hireable wanderer (`IsWanderer && CompanionOf == null`) from `HeroesWithoutParty` of a random town in the first half, then picks a random town in the second half: if that town also has a hireable wanderer, the two wanderers are removed with `LeaveSettlementAction.ApplyForCharacterOnly` and re-entered into each other's town with `EnterSettlementAction.ApplyForCharacterOnly` — a swap; if the second town has none, the first wanderer simply moves there. Net effect: at most one wanderer leaves a town per day, counts never change, hired wanderers never move, and (unlike the spawn predicate) no town is excluded — siege towns can receive or lose wanderers. There is no travel phase: the leave+enter pair is instantaneous, and `Hero.CharacterStates.Traveling` is used only by `TeleportHeroAction` (a debug/teleport helper), never by wanderer movement.

**"Standing in the tavern" is a separate, view-time layer.** The hero never physically lives in a tavern on the map; the tavern agent exists only while the player is inside the settlement's location complex. `HeroAgentSpawnCampaignBehavior` listens on `SettlementEntered`, `OnSettlementLeft`, `OnMissionEnded`, `OnGameLoadFinished`, governor changes and prisoner changes, and each refresh only runs when `LocationComplex.Current` (the complex of the settlement the player is currently in, via `PlayerEncounter.LocationEncounter`) equals the settlement's complex. It then takes the settlement's `HeroesWithoutParty` (plus lords, prisoners, party leaders) and asks the `HeroAgentLocationModel` game model where each hero belongs: `DefaultHeroAgentLocationModel.GetLocationForHero` returns `HeroLocationDetail.Wanderer` and `settlement.LocationComplex.GetLocationWithId("tavern")` for a wanderer (or hired `IsPlayerCompanion`) in a **town**, `"center"` in a castle, `"village_center"` in a village. New characters are added with `location.AddCharacter` or moved with `LocationComplex.ChangeLocation`; wanderers never list in the settlement overlay unless their `CurrentSettlement` equals the player party's current/last-visited settlement (`WillBeListedInOverlay`).

**The tavern agent itself.** `HeroAgentSpawnCampaignBehavior.CreateLocationCharacterForHero` builds the wanderer's `LocationCharacter`: spawn tag `"npc_common"`, `FixedLocation = true`, civilian equipment, no horse, faction colors deliberately *not* applied (wanderers keep neutral look), and the idle animation set `_warrior_in_tavern` (or `_warrior_in_aserai_tavern` in Aserai/Khuzait culture towns). When the player walks into the tavern location, `MissionAgentHandler.SpawnWanderingAgent` instantiates that character's agent on a usable spawn point found by tag — `SpecialTargetTag` first, falling back to `npc_common_limited`, then `npc_common`, i.e. the generic NPC spawn points inside the town/tavern scene.

**Where the tavern location comes from.** Each `Settlement` owns a `LocationComplex` (`Settlement.LocationComplex`) built in `Settlement.Deserialize` from the settlement XML's `<Locations complex_template="…"/>` reference. The templates are an MBObject type loaded at campaign init by `SandBoxManager.InitializeSandboxXMLs` via `MBObjectManager.LoadXML("LocationComplexTemplates")`; `LocationComplex.GetLocationWithId` is the lookup the placement model calls. In the default model the player's access to the tavern is never restricted (`DefaultSettlementAccessModel` returns true unconditionally from `CanMainHeroGoToTavern`). Note the tavern's staff are not heroes at all: `TavernEmployeesCampaignBehavior` spawns the tavernkeeper, wench, musician and ransom broker as culture `CharacterObject`s on dedicated spawn points (`spawnpoint_tavernkeeper`, `sp_tavern_wench`, `musician`) whenever a location mission opens the `"tavern"` location.

**Implications for the mod.** A mod companion only appears in a tavern if (a) it is in `Settlement.HeroesWithoutParty` (i.e. placed via `EnterSettlementAction.ApplyForCharacterOnly` and not in a party) and (b) a hero-agent-location model maps it to a location — vanilla maps `IsWanderer || IsPlayerCompanion`, so a hired mod companion sitting partyless in a town still gets a tavern agent. Movement is entirely `SwapCompanions` (unhired wanderers only, one per day) — a mod that wants "my companion follows me between towns" or wants to stop the daily shuffle must hook these two action calls or replace `HeroAgentLocationModel`, not touch scenes.

## Q4 — Hero creation

Status: VERIFIED

### Answer

**Entry API.** The API vanilla uses to turn a character template into a live wanderer hero is `HeroCreator.CreateSpecialHero(CharacterObject template, Settlement bornSettlement = null, Clan faction = null, Clan supporterOfClan = null, int age = -1)` — exactly what `CompanionsCampaignBehavior.CreateCompanionAndAddToSettlement` calls (wanderer template picked by demand score, a random town settlement matching the *template's* culture, `null` clan/supporter, `age = AgeModel.HeroComesOfAge + 5 + MBRandom.RandomInt(12)`), followed by `AdjustEquipments(hero)`, `hero.ChangeState(Hero.CharacterStates.Active)` and `EnterSettlementAction.ApplyForCharacterOnly`.

```csharp
public static Hero CreateSpecialHero(CharacterObject template, Settlement bornSettlement = null,
    Clan faction = null, Clan supporterOfClan = null, int age = -1)
```

The pipeline (everything after the builder is applied by the private `HeroCreator.InitializeHeroFromSettings`):

- **Age / birthday first** — `HeroCreationModel.GetBirthAndDeathDay(template, createAlive: true, age)` maps the age to a `BirthDay` (now − age years + a random day of the year) and `DeathDay = Never`. In `DefaultHeroCreationModel`: `age = -1` → age `HeroComesOfAge + RandomInt(30)`; `age = 0` → now; otherwise the given age — but for `Occupation.Wanderer` templates the passed age is **overridden**: `age = (int)template.Age + RandomInt(0..4)`, and if that is `< 20` a floor `12 + 4 × templateTraitLevel` is applied for every trait on the template. So for wanderers the XML `age` attribute of the template wins over the `age` argument (the spawner's 23–34 is discarded). `Hero.Age` is a float derived from `BirthDay`.
- **Template instantiation** — `HeroCreator.CreateHero(template, useCharacterAsTemplate: true)` calls `CharacterObject.CreateFrom(template)`: a fresh `CharacterObject` whose `OriginalCharacter` is the template, copying occupation/persona/traits and `FillFrom`-ing culture, race, level, XML age, `is_female`, the template's `DefaultCharacterSkills` (from its `skill_template` reference or inline `<skills>`), the `BodyPropertyRange` face min/max with hair/beard/tattoo tags, and the equipment rosters. XML parsing itself (`BasicCharacterObject.Deserialize`) supplies the template: `age` defaults to `max(20, BodyPropertyMax.Age)`, `level` to 1, plus `is_female`, `culture`, `skill_template`, `<face>` `BodyPropertiesMin/Max`/`face_key_template`, `EquipmentRoster`s.
- **Hero construction** — `new Hero(template.StringId, derivedCharacter, birthDay, deathDay)`: unique StringId via `CampaignObjectManager.FindNextUniqueStringId`, registration via `AddHero`, a living hero starts `NotSpawned`, and `SetCharacterObject` → `SetInitialValuesFromCharacter` snapshots the template into the hero: **traits** (every `TraitObject.All`, clamped per trait), Level, template name, Culture, `_defaultAge`, HitPoints = template `MaxHitPoints()`, IsFemale, Occupation = template's default occupation, and a random non-empty Battle/Civilian/Stealth **equipment** set cloned from the template (falling back to the `neutral_culture` `Default*EquipmentRoster`s when the template has none).
- **Builder** — `HeroInitializationArgs(hero, isOffspring: false)` copies those values and pre-rolls weight/build uniformly inside the template's `BodyPropertyRange` min/max (`CharacterHelper.GetDynamicBodyPropertiesBetweenMinMaxRange`); `CreateSpecialHero` adds `SetGenerateFirstAndFullName(true)` plus `SetBornSettlement`/`SetClan`/`SetSupporterOf` only when non-null.
- **Application order in `InitializeHeroFromSettings`** — parents, `IsFemale` (the template's unless an arg overrides — `CreateSpecialHero` never does), BornSettlement (arg ?? `GetBornSettlement`), formation, Clan (`GetClan` → null for template-born heroes: the wanderer is clanless), **culture** (arg ?? `GetCulture` → the *template's* culture, because a derived character inherits culture from its `OriginalCharacter`; the chosen town only fixes the spawn point), **body properties** (arg ?? `GetStaticBodyProperties` = random static face properties between the original template's BodyPropertiesMin/Max honouring hair/beard/tattoo tag restrictions; `SetAppearance` composes them with `DynamicBodyProperties(Hero.Age, Weight, Build)` and `FaceGen.SetHair`), SupporterOf, Level (template's), Weight/Build, then a culture-appropriate **name** via `NameGenerator.GenerateHeroNameAndHeroFullName` (because `GenerateFirstAndFullName` is set), occupation via `SetNewOccupation` only when it differs, **traits** from `GetTraitsForHero` (an empty list for parent-less template-born wanderers, so the template's trait levels simply stay), then **skills** from `GetDefaultSkillsForHero`: for heroes aged ≥ 18 every skill = the template `DefaultCharacterSkills` value + noise `+RandomInt(5,10)` with floor 1 (a 0 stays 0), written through `Hero.SetSkillValue` (no clamp); under 18 the list is empty.
- **Developer / attributes** — if `Age >= AgeModel.HeroComesOfAge` (default 18) `HeroDeveloper.InitializeHeroDeveloper()` runs: it re-derives XP/level from the skills (`TotalXp = Σ 2·skill^2.2 − 2000`, then `CheckLevel`), grants start points (focus `(level−1)·1 + 5`; attribute points `(level−1)/4 + 15`), bumps any 0-valued **attribute** to 1, initializes skill XP, and `DevelopCharacterStats()` auto-spends the remaining attribute points (`AddAttribute`, honouring the cap) and focus points and selects perks. Children get no developer at all.
- **Equipment (final)** — `HeroCreationModel.GetCivilianEquipment`/`GetBattleEquipment` return, for adults, the very equipment the hero already got from the template; both are re-assigned slot by slot (12 `EquipmentIndex` slots) onto the hero's `Equipment` objects with `EquipmentHelper.AssignHeroEquipmentFromEquipment`; `CampaignEventDispatcher.OnHeroCreated` fires. Afterwards the companion behavior quality-rolls the gear: `AdjustEquipments` rebuilds every armour/horse/weapon slot of both Battle and Civilian sets with `ItemModifier` objects `companion_armor` / `companion_weapon` / `companion_horse`.
- **Overridability** — every per-field decision above is a virtual hook of the `HeroCreationModel` game model (`GetBirthAndDeathDay`, `GetBornSettlement`, `GetStaticBodyProperties`, `GetClan`, `GetCulture`, `GetTraitsForHero`, `GetDefaultSkillsForHero`, `GetInheritedSkillsForHero`, `GenerateFirstAndFullName`, `GetCivilianEquipment`, `GetBattleEquipment`, `IsHeroCombatant`, …); a mod replaces the policy by registering a `GameComponent<HeroCreationModel>` subclass, which is the intended path for custom companion creation.

## Q5 — Character templates

Status: VERIFIED

### Answer

**A wanderer template is not a special object type.** It is an ordinary `NPCCharacter` element registered under the object-list id `NPCCharacters`, carrying `is_template="true"` and `occupation="Wanderer"`. `Campaign` registers the type as `RegisterType<CharacterObject>("NPCCharacter", "NPCCharacters", 16u)` (element name `NPCCharacter`, list name `NPCCharacters`; the multiplayer twin `BasicCharacterObject` shares the element name under list `MPCharacters`), and `SandBoxManager.InitializeSandboxXMLs` calls `MBObjectManager.Instance.LoadXML("NPCCharacters")` while the campaign is being set up. The *file name* is irrelevant: `XmlResource.GetXmlListAndApply` reads each module's `SubModule.xml`, and every `<Xmls><XmlNode><XmlName id="NPCCharacters" path="ModuleData/whatever"/></XmlNode></Xmls>` entry becomes an `MbObjectXmlInformation` (`Id` = list name, `Name` = path, `ModuleName`, optional `IncludedGameTypes`). `MBObjectManager.LoadXML` → `GetMergedXmlForManaged` merges all active modules' files sharing that id (XSD-validated, optional XSLT, game-type filter) and `LoadXml` deserializes every child node of the merged document. `ModuleHelper.GetXmlPath` resolves the path to `<module>/ModuleData/<path>.xml`, and the schema `ModuleHelper.GetXsdPath` looks for is the install's `XmlSchemas/<id>.xsd` — the extracted copy `~/bannerlord/xmlschemas/NPCCharacters.xsd` exists, declares root element `NPCCharacters` with `NPCCharacter` children, a `<xs:unique>` rule on `@id`, `culture` **required** with pattern `Culture\..+`, and `AlwaysPreferMerge` annotations on `face`, `face_key`, `BodyProperties` and `Resistances`.

**What the merge does with two files claiming the same id.** `XmlResource.GetXmlListAndApply` feeds the schema into `XmlResource.XsdElementDictionary` (`ReadXsdFileAndExtractInformation` stores each element's XPath, its `AlwaysPreferMerge` note and the `UniqueAttributes` taken from `<xs:unique>`/`<xs:key>`), `GetMergedXmlForManaged` prefers a per-module `ModuleData/XmlSchemas/<id>.xsd` (`ModuleHelper.GetXsdPathForModules`) and falls back to the base schema, and `MergeTwoXmls` then either appends the second file's children verbatim (when the XSD path is the empty string) or runs `MergeElements`, which merges attributes, honours `_replaceWhileMerging="true"` (drop the old element's attributes/children first) and matches elements by their unique attributes — so a later module redefining `<NPCCharacter id="…">` patches the existing entry instead of duplicating it, and an unknown id is appended. Validation itself is not fatal: `LoadXmlWithValidation` catches a missing/invalid XSD, prints `xsd file of … could not be found!`, and loads the document anyway, and `MBObjectManager.LoadXML` wraps `LoadXml` in an empty `catch (Exception)` — a template file that throws during deserialization disappears silently.

**Which module, in vanilla.** The local extract contains **zero** `occupation="Wanderer"` attributes (197 `Soldier`, 135 `Townsfolk`, 55 `Villager`, 45 `Special`, 36 `Lord`, …), so the vanilla wanderer template file was not extracted. Its supporting data is in **SandBoxCore**: 68 `SkillSet` ids `spc_wanderer_<culture>_<n>_skills` and the `EquipmentRoster` ids `npc_wanderer_equipment_template_<culture>`, `npc_wanderer_equipment_template_<culture>_civilian`, `npc_armed_wanderer_equipment_template_<culture>` (all six main cultures). Those names are the surviving halves of the vanilla templates (see Uncertain for the file itself).

**Element and attribute grammar** (read off the deserializers, cross-checked against `NPCCharacters.xsd`):
- identity / shared part — `MBObjectBase.Deserialize` takes `id`; `BasicCharacterObject.Deserialize` takes `name` (a `{=!}` localisation string), `race`, `occupation` (only used here to set `IsSoldier`), `is_hero`, `face_mesh_cache`, `is_obsolete`, `culture` as an object reference (`Culture.` prefix + the bare `id` from `spcultures.xml`: `empire`, `aserai`, `sturgia`, `vlandia`, `battania`, `khuzait`), `age` (default `max(20, BodyPropertyMax.Age)`), `level` (default 1), `is_female`, `default_group`, `formation_position_preference`, `default_equipment_set`, and `skill_template="SkillSet.<id>"` (falls back to an auto-created `MBCharacterSkills`).
- child elements — `<skills>`/`<Skills>` with `<skill id="Athletics" value="30"/>`; `<face>` with `<face_key_template value="BodyProperty.<id>"/>` (the `MBBodyProperty` age/weight/build range) plus `hair_tags`/`beard_tags`/`tattoo_tags` (`<tag name=…/>`) and `<BodyProperties>`/`<BodyPropertiesMax>`; `<Equipments>` holding either an **inline** `<EquipmentRoster>` (`Init` → `equipmentType="Civilian"` or the deprecated `civilian="true"`, children `<equipment slot="Item0" id="Item.…"/>`) or an **import** `<EquipmentSet id="<EquipmentRoster id>" equipmentType="…"/>`, which is resolved with `GetObject<MBEquipmentRoster>(id)` + `AddEquipmentRoster`; `<Resistances knockback= knockdown= dismount=>`.
- campaign-only part — `CharacterObject.Deserialize` reads `occupation` via `Enum.Parse` on the `Occupation` enum (so `occupation="Wanderer"`), `is_template`, `is_hidden_encyclopedia`, `voice`, `is_basic_troop`, `upgrade_requires`, `level`, `civilianTemplate`/`battleTemplate` (deprecated), `<Traits>` and `<upgrade_targets><upgrade_target id="NPCCharacter.…"/></upgrade_targets>`. A template that omits `occupation` keeps `Occupation.NotAssigned`: the extract's own `npc_wanderer_equipment_template_empire` template has no `occupation`, so despite its name it is *not* a wanderer. `is_mariner` is derived, not read: `_isMariner = GetTraitLevel(DefaultTraits.NavalSoldier) != 0`.
- schema vs code — `NPCCharacters.xsd` types `is_template` as an optional `xs:boolean`, leaves `occupation` a plain `xs:string` (any value that is not an `Occupation` member dies in the runtime `Enum.Parse`), and makes `culture` **required** with the pattern `Culture\..+`, which is why every vanilla entry writes `culture="Culture.empire"`. The schema also declares `is_child_template`, `is_companion` and `is_mercenary`, but no decompiled code reads those three attribute names (`IsChildTemplate` is declared and never assigned), so they are dead weight for a mod.

**How wanderer templates are picked at runtime.** There is no culture-side wanderer list. `CompanionsCampaignBehavior.InitializeCompanionTemplateList` and `CharacterHelper.GetRandomCompanionTemplateWithPredicate` both walk the live list `MBObjectManager.Instance.GetObjectTypeList<CharacterObject>()` (the same list `Campaign.Characters` and `CharacterObject.All` expose) and keep `x.IsTemplate && x.Occupation == Occupation.Wanderer`. Each template is classified by `GetTemplateTypeOfCompanion` (`IsMariner` → Sailor, otherwise the highest skill above 20) and the spawn town is chosen as any `Town` whose `Culture` equals the **template's own** culture, then `HeroCreator.CreateSpecialHero(companionTemplate, settlement, null, null, AgeModel.HeroComesOfAge + 5 + MBRandom.RandomInt(12))`. Occupation-driven creation for other occupations (`HeroCreator.CreateNotable`) instead goes through `DefaultHeroCreationModel.GetRandomTemplateByOccupation`, which reads `settlement.Culture.NotableTemplates` (filled from `<notable_templates>` children in `spcultures.xml`) weighted by `DefaultTraits.Frequency`; wanderers never use that path.

**Can a mod create a hero at runtime without an XML template? Yes for the hero; no for making a real template.**
- The game itself creates `CharacterObject`s with no XML: `CharacterObject.CreateFrom(...)` begins with `MBObjectManager.Instance.CreateObject<CharacterObject>()`, and `CreateObject<T>(stringId)` / `CreateObject<T>()` are literally `new T { StringId = … }; RegisterObject(val)` plus the `IObjectManagerHandler.AfterCreateObject` callbacks. `CharacterObject`'s parameterless ctor is public (`Init()` → `_occupation = Occupation.NotAssigned`, `Level = 1`), `RegisterObject<T>` / `RegisterPresumedObject<T>` are public, `MBObjectBase.StringId` has a public setter, and a duplicate id is automatically re-suffixed with digits. Such an object is immediately visible through `CharacterObject.All`.
- Turning one into a hero needs no XML either: `HeroCreator.CreateSpecialHero(CharacterObject template, Settlement bornSettlement = null, Clan faction = null, Clan supporterOfClan = null, int age = -1)` never inspects `IsTemplate` — it runs `CreateHero(template, useCharacterAsTemplate: true, …)` → `CharacterObject.CreateFrom(template)` → `new Hero(character.StringId, character, birthDay, deathDay)` (id made unique by `CampaignObjectManager.FindNextUniqueStringId<Hero>`). `HeroCreator.CreateBasicHero(string stringId, CharacterObject character, out Hero hero, bool isAlive = true)` skips the clone entirely (`useCharacterAsTemplate: false`) and adopts an existing instance.
- What pure C# **cannot** do is make that object behave as a template: `IsTemplate` is `{ get; private set; }` and the only assignment anywhere in the decompiled sources is `is_template` in `CharacterObject.Deserialize`; `_occupation` has no setter at all (only `GetDefaultOccupation()` reads it); `SetName`, `DefaultCharacterSkills`, the equipment roster and `BodyPropertyRange` are private/protected. Publicly settable: `Culture`, `Age`, `Level`, `IsFemale`, `Race`, `DefaultFormationGroup`, `IsBasicTroop`, `FaceDirtAmount`. A hand-built `CharacterObject` therefore has `IsTemplate == false`, is invisible to both wanderer pools, and arrives nameless, skill-less, equipment-less and face-less.
- The no-XML-*file* workaround the engine itself supports: build the document in memory and hand it to the object manager — `MBObjectManager.LoadXml(XmlDocument doc, bool isDevelopment = false)` matches the root child against a registered `ElementListName` (`NPCCharacters`) and deserializes every child node, and `CreateObjectFromXmlNode(XmlNode node)` / `CreateObjectFromXmlNode(node, "NPCCharacter")` do a single node (presumed object → `Deserialize` → `AfterInitialized`). That yields a genuine `is_template="true"` + `occupation="Wanderer"` template from a string (e.g. generated from the mod's JSON) with no `SubModule.xml` entry and no module file.
- Hero occupation, unlike character occupation, is runtime-mutable: `Hero.SetNewOccupation(Occupation)` is public and fires `OnHeroOccupationChanged`; `Hero.IsWanderer` is simply `Occupation == Occupation.Wanderer`; and because `CharacterObject.Occupation` returns `HeroObject.Occupation` once the character belongs to a hero, a hero born from any template can be switched to wanderer afterwards. The initial value comes from `CharacterObject.GetDefaultOccupation()`, which is why a wanderer template is the normal way to get wanderer heroes.

## Q6 — Hiring

Status: VERIFIED

### Answer

**Where the flow lives.** The whole vanilla wanderer hire flow is conversation lines plus condition/consequence callbacks inside one behavior, `LordConversationsCampaignBehavior`: `OnSessionLaunched` calls `AddDialogs`, which registers the wanderer meet line and then `AddWandererConversations` / `AddHeroGeneralConversations`. There is no hire button or UI, the player simply talks to the wanderer, who per Q1 sits in a tavern settlement with `PartyBelongedTo == null`. The `CampaignGameStarter.AddDialogLine` / `AddPlayerLine` node graph itself is Q7's subject; here only the wanderer-specific nodes and gates are documented.

**First meeting.** The NPC line `start_wanderer_unmet` (node `start` → `wanderer_meet_player_response`, text `{VOICED_LINE}`, priority 110) shows when `conversation_wanderer_meet_on_condition`: the conversation character is a hero with `Occupation == Occupation.Wanderer` and not in the `Prisoner` state (`conversation_wanderer_on_condition`), and the first-meeting gate `ConversationUseMeetingDialogs()` passes (true only on the first conversation: it calls `SetHasMet`, marks `ConversationManager.CurrentConversationIsFirst` and plays the voiced greeting). The player answers with `wanderer_meet_player_response1/2` (`conversation_wanderer_meet_player_on_condition`), then a backstory chain runs (`wanderer_prebackstory` → `wanderer_introduction_a/b/c` → player reaction `{BACKSTORY_RESPONSE_1/2}` → `wanderer_introduction_d` → `wanderer_job_status` → hub): the story texts are fetched per wanderer template via `GameTexts.FindText("backstory_a", template.StringId)` etc., and the template is remembered in `_previouslyMetWandererTemplates` so a second wanderer of the same template gets the generic-backstory line instead. The hub is `hero_main_options`; for an already-hired wanderer the job-status line names the employer from `CompanionOf.Name`.

**Hire entry.** `main_option_faction_hire`, a player line on `hero_main_options` → node `companion_hire` ("I can use someone like you in my company."), is shown when `conversation_hero_hire_on_condition`: conversation hero exists, `!IsPlayerCompanion`, `conversation_wanderer_on_condition()` and `PartyBelongedTo == null`.

**Cost presentation.** The NPC line `companion_hire` → `player_companion_hire_response` is set up by `conversation_companion_hire_gold_on_condition`: `GOLD_AMOUNT` := `Campaign.Current.Models.CompanionHiringPriceCalculationModel.GetCompanionHiringPrice(Hero.OneToOneConversationHero)`, then one of seven persona/trait-flavoured `HIRING_COST_EXPLANATION` texts ("...I'm going to need about {GOLD_AMOUNT}{GOLD_ICON} to settle up some debts...", down-payment/advance variants); it always returns true. The vanilla price, `DefaultCompanionHiringPriceCalculationModel.GetCompanionHiringPrice` (bound in `SandBoxManager.Initialize`), = 1/2 x (every slot of the wanderer's combat `Equipment` plus the first civilian equipment set, priced with `Town.GetItemPrice` of the hero's current settlement's town, nearest town to the main party if none) + `CharacterObject.Level` x 10, times 0.75 if the player is party leader and owns the Steward perk `PaidInPromise`, plus the `Trade.GreatInvestor` party perk adjustment. It is an abstract `CompanionHiringPriceCalculationModel` game model, so a mod can swap the price formula.

**Branches.** Three player lines on `player_companion_hire_response`: (a) `companion_hire_capacity_full` ("Thinking again, I already have more companions than I can manage.") → node `lord_pretalk`, shown when `too_many_companions()`; (b) accept `player_companion_hire_response_1` ("Right... {GOLD_AMOUNT} Here you are.") → `hero_leave`, condition `conversation_companion_hire_on_condition` = `Hero.MainHero.Gold` strictly greater than the price AND `!too_many_companions()` (the line's own condition renders the price through the `str_STR1_STR2` text trick), consequence `conversation_companion_hire_on_consequence`; (c) decline `player_companion_hire_response_2` ("I can't afford that just now.") → `lord_pretalk`, condition only `!too_many_companions()`, a vanilla quirk: visible even when the player can pay. Both refusals land on `lord_pretalk`, which loops back to `hero_main_options` ("Is there anything else?"); acceptance continues `hero_leave` → farewell variations → `close_window`.

**The accept consequence** is exactly three actions in this order (gold first, then clan, then party):

1. `GiveGoldAction.ApplyBetweenCharacters(Hero.MainHero, Hero.OneToOneConversationHero, price)` — price from `CompanionHiringPriceCalculationModel.GetCompanionHiringPrice`.
2. `AddCompanionAction.Apply(Clan.PlayerClan, Hero.OneToOneConversationHero)`.
3. `AddHeroToPartyAction.Apply(Hero.OneToOneConversationHero, MobileParty.MainParty)`.

**How the wanderer joins the clan.** The join mechanism is the `Hero.CompanionOf` property, not the `Hero.Clan` setter: `AddCompanionAction.Apply(clan, hero)` first fires any current employer (`RemoveCompanionAction.ApplyByFire`, cf. Q2), assigns `companion.CompanionOf = clan`, and dispatches `OnNewCompanionAdded`. The `CompanionOf` setter does the clan bookkeeping: resets `_homeSettlement`, removes the hero from the old clan and adds it to the new via `Clan.OnCompanionAdded` → `_companionsCache.Add`; `IsPlayerCompanion` is just `CompanionOf == Clan.PlayerClan`, and `Hero.Clan`'s getter returns `CompanionOf ?? _clan`, so a hired wanderer *reports* the player clan while its own `_clan` field stays `null`. SandBox behaviours react through the `CampaignEvents.NewCompanionAdded` event (the Q8 hook family), e.g. `ClanMemberRolesCampaignBehavior` spawns the companion's location agent in the current location complex. `AddHeroToPartyAction.Apply(hero, MobileParty.MainParty)` decrements the old party's member roster, clears `StayingInSettlement`, adds the hero to the new party roster, dispatches `OnHeroJoinedParty`, and shows the `str_companion_added` toast because the hero is a player companion in the main party. A grep over all decompiled sources finds exactly three `AddCompanionAction.Apply` call sites (this dialog, the `LordsNeedsTutorIssueBehavior` and `FamilyFeudIssueBehavior` quest rewards), so the hire dialog is the only way a wanderer becomes a player companion in vanilla.

**Cost handling.** `GiveGoldAction.ApplyBetweenCharacters` is a hero-to-hero transfer: internally it clamps the amount with `MathF.Min(giverHero.Gold, goldAmount)` via `ChangeHeroGold` and dispatches `OnHeroOrPartyTradedGold`; the dialog condition already guarantees full affordability, so the clamp never bites in vanilla, and paying before `AddCompanionAction.Apply` means a hire can never end up companion-without-payment.

**Companion limit check.** The limit is enforced **dialog-side only**: `too_many_companions()` = `Clan.PlayerClan.Companions.Count >= Clan.PlayerClan.CompanionLimit` gates both the capacity line and the accept line. `Clan.CompanionLimit` delegates to `Campaign.Current.Models.ClanTierModel.GetCompanionLimit(this)` (bound to `DefaultClanTierModel` in the same `SandBoxManager.Initialize`): the default returns `clan.Tier + 3` plus `+1` for the clan leader's Leadership perk `WePledgeOurSwords` and `+1` for the Charm perk `Camaraderie` (clan tiers are bounded 0-6). `AddCompanionAction.Apply` itself contains no limit check and no gold check; it happily exceeds the limit and even re-fires an existing employer.

**Orchestrator notes (verified).** Mod hiring with a JSON `hireCost` = the same three actions with `hireCost` as the amount, gated by `Hero.MainHero.Gold > hireCost` (vanilla uses strict `>`) and the vanilla limit `Clan.PlayerClan.Companions.Count >= Clan.PlayerClan.CompanionLimit`. Because mod companions are `IsWanderer` and partyless in a town, the vanilla `main_option_faction_hire` line (`conversation_hero_hire_on_condition`) would also be offered for them, at the vanilla model price; the mod's dialog registration must either take priority over or exclude that path for mod companions (Q7 decides how).

## Q7 — Dialog API

Status: VERIFIED

### Answer

**The registration funnel.** Dialog lines are not data files — they are in-memory records `(id, inputToken, outputToken, text, condition, consequence, priority, flags)` that campaign behaviors append to `ConversationManager._sentences` (a private `List<ConversationSentence>`, no getter) at session launch. The vanilla pattern: a `CampaignBehaviorBase` subclass subscribes a `private void OnSessionLaunched(CampaignGameStarter)` handler to `CampaignEvents.OnSessionLaunchedEvent` from its `RegisterEvents()` (which runs when the behavior is added to the campaign), and that handler registers the whole graph. `LordConversationsCampaignBehavior` alone makes 461 `starter.AddDialogLine`/`AddPlayerLine` calls. The public entry points are on `CampaignGameStarter` (signatures paraphrased):

```
AddDialogLine(id, inToken, outToken, text, cond, cons, priority = 100, [clickableCond])                  // NPC line
AddPlayerLine(id, inToken, outToken, text, cond, cons, priority = 100, [clickableCond], [persuasionOpt]) // player option
AddRepeatablePlayerLine(id, ..., continueText, continueOutToken, cond, cons, priority = 100, ...)         // one option per repeat object
AddDialogLineWithVariation(id, inToken, outToken, cond, cons, priority = 100, ...)                       // text picked from tagged GameTexts
AddDialogLineMultiAgent(id, ..., agentIndex, nextAgentIndex, priority = 100, ...)                        // multi-agent scenes
AddDialogFlow(flow, relatedObject = null)  // + DialogFlow.CreateDialogFlow(inToken, priority) fluent builder
```

All funnel into `ConversationManager.AddDialogLine(ConversationSentence)` (internal — mods cannot construct `ConversationSentence` directly; its ctor is internal), which appends and keeps the list sorted (below); `AddDialogFlow` expands a `DialogFlow` into lines carrying the given `relatedObject`. `Campaign.OnSessionStart` runs all the launch listeners first, then calls `ConversationManager.Build()` for a final stable sort. A legacy XML-attribute loader `ConversationSentence.Deserialize` exists but has no caller in the extract — decomp shows only delegate-based registration.

**Token/state system.** Each line is an edge `inputToken → outputToken` in a finite-state graph. Tokens are arbitrary strings interned to ints by `ConversationManager.GetStateIndex`: five are pre-seeded in the ctor's `stateMap` — `start` = 0, `event_triggered` = 1, `member_chat` = 2, `prisoner_chat` = 3, `close_window` = 4 (mirrored by the `ConversationToken` enum) — every other token is created on first use, which is why tokens like `hero_main_options` (constant `QuestManager.HeroMainOptionsToken`), `lord_pretalk`/`lord_start` (`ConversationTokens.LordPretalk`) or `companion_hire` (Q6) are nowhere centrally declared; `DialogFlow` auto-generates `atk:N` tokens for unnamed nodes. `ConversationManager.ActiveToken` is the current node: firing a line sets it to that line's output token; every conversation entry point (`OpenMapConversation`, `SetupAndStartMapConversation`, `SetupAndStartMissionConversation`) calls `StartNew(0, …)` so conversations always begin at `start`, then `ProcessPartnerSentence()` makes the NPC speak before the player gets options. `IsConversationEnded()` is literally `ActiveToken == 4` — the graph closes by routing a line's output to `close_window` (DialogFlow's `CloseDialog()` sets exactly that) — and `DoOptionContinue` ends the conversation when the token is `close_window` and the last processed line was a player line. Conditions with side effects on invisible lines are a vanilla idiom (Q6's `set_vars` line on `start`→`lord_intro`, text "Never see this").

**Conditions, clickable gates, consequences.** `ConversationSentence.OnConditionDelegate` is `bool ()` — it takes no arguments, so context comes from live game state: `Hero.OneToOneConversationHero` (a proxy for `ConversationManager.OneToOneConversationHero`), `Campaign.Current.CurrentConversationContext`, `ConversationHelper` statics. Conditions re-run every time the option list is (re)built (`GetSentenceOptions` → `RunCondition()` per candidate) — there is no caching, state changes between frames take effect immediately. `OnClickableConditionDelegate(out TextObject explanation)` is a second gate on player options: condition true but clickable false renders the option grayed-out with the explanation text (vanilla example: `main_option_hostile_1_2` "I want to take revenge" with `conversation_player_can_attack_hero_on_clickable_condition`). Consequences run on selection: `ProcessSentence` advances `ActiveToken` first, then `RunConsequence(Game)` fires the line's `OnConsequence` (persuasion options commit points via `OnPersuasionOptionDelegate`). Sentence flags: `PlayerLine`, `RepeatForObjects` (repeatable lines expand into one option per object from `ConversationSentence.SetObjectsToRepeatOver`, max 5 per conversation plus an auto `_continue` option — this is the Q6 hire-list mechanism), `UsedOnce` (the sentence index goes into `_usedIndices` after firing and the line is skipped for the rest of the conversation; `StartNew` clears it), and special/persuasion styling.

**Priority and how order/choice is decided.** Priority is a plain int, default 100 (`ConversationSentence.DefaultPriority`). `_sentences` is kept sorted by priority descending: each `AddDialogLine` inserts via `SortLastSentence` (it shifts earlier sentences only while their priority is strictly lower, so a new line lands after every line with priority ≥ its own — ties keep registration order), and `Build()`/`EnableSentenceSort()` re-sort with a stable `OrderByDescending`; bulk registrars wrap in `DisableSentenceSort`/`EnableSentenceSort` (issues do this at new-game). Selection differs by side:

- **NPC lines:** only the FIRST passing match at `ActiveToken` can fire — `ProcessPartnerSentence` calls `GetSentenceOptions(onlyPlayer: false, processAfterOneOption: false)` (returns at the first match) and takes `sentenceOptions[0]`. For NPC lines priority is winner-take-all: the priority-110 greetings at `start` (`start_lord_unmet` etc., Q6) shadow the priority-100 `start_default` whenever both conditions pass.
- **Player options:** ALL lines passing `GetSentenceMatch` (input token == `ActiveToken`, `IsPlayer`, UsedOnce not spent) on the current token become listed options — `GetPlayerSentenceOptions` calls `GetSentenceOptions(onlyPlayer: true, processAfterOneOption: true)` and the loop keeps going (the flag name means "process on after one option": it does NOT stop at the first). Priority only **orders** the list, it never hides a player option: on `hero_main_options`, `hero_give_issue` (110) shows above `main_option_faction_hire` (100, the default — `AddHeroGeneralConversations` passes no priority) above "I must leave now." (`player_is_leaving_neutral_or_friendly`, priority 1, deliberately last). `ContinueConversation` waits for a player choice whenever `CurOptions.Count > 1`. Quests/issues exploit the ordering: story quests register flows at priority 125–700 on `hero_main_options` (e.g. `SupportKingdomQuest.GetImperialKingDialogueFlow` uses 300) so their option appears on top, not instead, of the vanilla hub options.

**Mod scenario — adding a hub line, and suppressing vanilla hire for mod heroes.** (a) Add a mod behavior whose `OnSessionLaunched` listener calls `starter.AddPlayerLine("mod_id", "hero_main_options", "companion_hire", text, cond, cons, 110)` where `cond` checks `Hero.OneToOneConversationHero.StringId` against the mod JSON registry (Q2) — the line appears in the vanilla hub list sorted above the vanilla 100-priority options. Consequences bind to lines, not tokens, so the mod line must carry its own consequence; its output token may reuse the vanilla hire subgraph node (`companion_hire`, Q6) or a private token of the mod's own. Mid-campaign (de)registration uses the quest/issue pattern: register via `AddDialogFlow` or the `DialogFlow.AddPlayerLine(..., relatedObject, ...)` overloads, which stamp a `RelatedObject`, then `ConversationManager.RemoveRelatedLines(relatedObject)` removes exactly those lines (the `QuestBase`/`IssueBase`/`IssueManager` cleanup pattern). (b) Suppressing vanilla `main_option_faction_hire` for specific heroes **cannot be done with priority**: every passing player option is listed (above), so a higher-priority mod line only reorders the menu — the vanilla hire option still shows for mod heroes because they satisfy `conversation_hero_hire_on_condition` (non-companion wanderer, not prisoner, `PartyBelongedTo == null` — exactly what Q1/Q2 produce). Nor with removal: `ConversationManager.RemoveRelatedLines` only reaches lines registered with a `relatedObject`, and the `CampaignGameStarter.AddDialogLine`/`AddPlayerLine` overloads always pass `relatedObject = null`, so vanilla hub lines are unremovable individually; `_sentences` is private with no getter, and while `ConversationSentence.OnCondition` is a public mutable field, sentence instances are unreachable without reflection into that private list (fragile, not an API). The only clean, targeted suppression in decomp is a **Harmony prefix on `LordConversationsCampaignBehavior.conversation_hero_hire_on_condition`** (private instance method — Harmony handles it via `AccessTools`) returning `false` when `Hero.OneToOneConversationHero` is a mod-registry hero: that method is the condition of `main_option_faction_hire` alone, so the option disappears for those heroes only. The blunt non-Harmony alternative — `Campaign.Current.CampaignBehaviorManager.RemoveBehavior<LordConversationsCampaignBehavior>()`, which also clears the behavior's event listeners (StoryMode uses this API on its phase behaviors) — would erase all 461 vanilla lord/wanderer conversation lines to suppress one; not practical.

**Orchestrator note (verified).** `conversation_hero_hire_on_condition` is referenced only by `main_option_faction_hire` (LordConversationsCampaignBehavior line 797), and `GetSentenceOptions` returns early only when `processAfterOneOption` is false (NPC side), so every passing player option is listed. Decision: suppress the vanilla hire option for registry heroes with a Harmony prefix on that method (second patch, M3 task 28); the mod registers its own hire line on `hero_main_options`.

## Q8 — Campaign lifecycle hooks

Status: VERIFIED

### Answer

**Where campaign logic lives.** A mod's campaign-side logic is a `CampaignBehaviorBase` subclass with two abstract members: `RegisterEvents()` (subscribe to the static `CampaignEvents.*Event` events, in vanilla always via `AddNonSerializedListener(this, Handler)`) and `SyncData(IDataStore dataStore)` (persistence). Behaviors are collected in a `CampaignGameStarter`: vanilla adds its roster in `SandBoxManager.Initialize`, and modules add theirs from the `MBSubModuleBase.InitializeGameStarter(Game, IGameStarter)` hook that `MBGameManager` fans out to every active module — first-party example: `StoryModeSubModule.InitializeGameStarter` calling `campaignGameStarter.AddBehavior(...)`. A mod that wants its behavior in the campaign registers it the same way. `CampaignBehaviorManager.RegisterEvents()` then runs exactly once per session — on the saved-campaign path right after `LoadBehaviorData()` inside `Campaign.OnInitialize`, on the new-game path inside `Campaign.OnNewGameCreatedInternal` — so listeners never need saving (they are re-registered every session). A behavior added later via `CampaignBehaviorManager.AddBehavior` gets `RegisterEvents()` immediately.

**1. "New game created" → `CampaignEvents.OnNewGameCreatedEvent`.** An `IMbEvent<CampaignGameStarter>` that fires only for `GameLoadingType.NewCampaign`. Sequence: `Campaign.DoLoadingForGameType` reaches `PostInitializeFourthState` → private `Campaign.OnNewGameCreated(starter)` → `OnNewGameCreatedInternal` (generates `UniqueGameId`, sets `TimeControlMode = Stop`, calls `CampaignBehaviorManager.RegisterEvents()`) → `CampaignEventDispatcher.Instance.OnNewGameCreated` fan-out → the `CampaignEvents` receiver override invokes `OnNewGameCreatedEvent`, then `OnNewGameCreatedPartialFollowUpEvent` 100 times (indexed 0..99 for staged follow-ups), then `OnNewGameCreatedPartialFollowUpEndEvent`. This is the seeding hook — vanilla `CompanionsCampaignBehavior` spawns its wanderers here. It fires before `OnSessionLaunchedEvent`, which fires for **both** flows via `Campaign.OnSessionStart` and is the only "something happened, campaign is up" event shared by new and loaded games.

**2. "Game loaded" → `CampaignEvents.OnGameLoadFinishedEvent` for rebuilds.** Vanilla behaviors use this no-argument event as the post-load rebuild hook (`CompanionsCampaignBehavior.OnGameLoadFinished` refills its companion lists). Its only decomp trigger is `SandBoxGameManager.OnLoadFinished` in the `LoadingSavedGame` branch: after `MapState` is pushed and `CampaignInformationManager.OnGameLoaded()` runs, it casts `CampaignEventDispatcher.Instance` to `CampaignEventReceiver` and calls `OnGameLoadFinished()`, which fans out to the `CampaignEvents` receiver and invokes the event. Earlier in the same flow, `Campaign.OnGameLoaded(starter)` fires `OnGameEarlyLoadedEvent` then `OnGameLoadedEvent(CampaignGameStarter)`. Important asymmetry: the new-game branch of `OnLoadFinished` plays the intro video / opens character creation and never touches that fan-out, so `OnGameLoadFinishedEvent` appears saved-load only (see Uncertain). Crucially, saved `SyncData` records are already restored **before** any load event: `Campaign.OnInitialize` (SavedCampaign) runs `InitializeCampaignBehaviors` → `LoadBehaviorData()` → `RegisterEvents()`, so rebuild listeners see restored fields. The vanilla pairing for "do it on every session" is exactly what `CompanionsCampaignBehavior` does: `OnNewGameCreatedEvent` + `OnGameLoadFinishedEvent` (both already used by the mod behavior per Q1).

**3. "Daily tick" → `CampaignEvents.DailyTickEvent`.** A no-argument `IMbEvent`; `WeeklyTickEvent` sits beside it. Mechanism: `Campaign.OnDataLoadFinished` (runs for both flows) calls `CampaignPeriodicEventManager.InitializeTickers()` and `Campaign.CreateCampaignEvents()`, which creates one periodic campaign event via `CampaignPeriodicEventManager.CreatePeriodicEvent(CampaignTime.Days(1f), …)` with `Campaign.DailyTick` as its handler; that handler calls `CampaignEventDispatcher.Instance.DailyTick()` (fan-out → `CampaignEvents` receiver invokes `DailyTickEvent`) and additionally `WeeklyTick()` every `CampaignTime.DaysInWeek` elapsed days. The periodic clock only advances while the campaign tick has `_dt > 0` (`Campaign.Tick`) — no daily ticks while time is stopped (menus, pause, `TimeControlMode.Stop`). For load spreading, vanilla also exposes per-entity daily variants (`DailyTickPartyEvent`, `DailyTickTownEvent`, `DailyTickSettlementEvent`, `DailyTickHeroEvent`, `DailyTickClanEvent`) whose fan-outs are scheduled per entity by `CampaignPeriodicEventManager.InitializeTickers`.

**4. Persistence → override `SyncData(IDataStore)`.** The contract is `IDataStore.SyncData<T>(string key, ref T data)`, called with the *same* key/field on save and load; `BehaviorSaveData.SyncData` adds `(key, data)` to a `Dictionary<string, object>` when saving and reads/casts it back when loading. Canonical vanilla shape (`CaravansCampaignBehavior.SyncData`): one `dataStore.SyncData("<key>", ref <field>)` call per persisted field.

Save hook: `SaveHandler.SaveTick` → `CampaignEventDispatcher.Instance.OnBeforeSave()` → `CampaignEvents.OnBeforeSaveEvent` → `CampaignBehaviorManager.OnBeforeSave` (subscribed at manager construction) → `CampaignBehaviorDataStore.SaveBehaviorData` per behavior. Load hook: `Campaign.OnInitialize` (SavedCampaign) → `CampaignBehaviorManager.LoadBehaviorData`. Each behavior's records live in a `BehaviorSaveData` keyed by `CampaignBehaviorBase.StringId` (defaults to `GetType().Name`); loading prefers an exact StringId hit, else falls back to the stored key that *contains* the behavior's current type name (rename-tolerant). The store objects ship inside the save file (`CampaignBehaviorDataStore`, its nested `BehaviorSaveData` and `CampaignBehaviorManager` are save-registered classes). **What is saveable:** anything `TaleWorlds.SaveSystem` can serialize, which means the exact container instantiation must be registered — `Dictionary<string, Hero>` *is* registered in vanilla's `SaveableCampaignTypeDefiner.DefineContainerDefinitions`, so it works as a synced field out of the box (vanilla itself syncs e.g. a `List<Hero>` in `LordsNeedsTutorIssueBehavior.SyncData`). Custom classes/containers need a `SaveableTypeDefiner` subclass whose constructor reserves an id range (vanilla features use offsets like 380000) and whose `DefineClassTypes`/`DefineContainerDefinitions` register the types; every non-abstract definer in a save-referencing assembly is instantiated automatically by `DefinitionContext.CollectTypes` — vanilla per-feature examples are nested right inside their behavior (e.g. `CaravanAmbushIssueTypeDefiner`). Alternatively a behavior can persist nothing (empty `SyncData` override) and rebuild derived state on `OnGameLoadFinishedEvent` — what `CompanionsCampaignBehavior` does.

**Orchestrator note (verified).** `SaveableCampaignTypeDefiner` registers `Dictionary<string, Hero>` (line 531), so the mod's companion id → hero map can be a synced field with no custom `SaveableTypeDefiner`. `OnGameLoadFinished` is raised only in the `LoadingSavedGame` branch of `SandBoxGameManager.OnLoadFinished` (line 177 inside the `else` of `if (!LoadingSavedGame)`), so new-game spawning must use `OnNewGameCreatedEvent`.

## Q9 — Existing saves

Status: VERIFIED

### Answer

**What happens when a save created without the mod is loaded with it enabled: the mod is grafted onto the old save before any load event fires, and only the data is genuinely missing — the logic and templates are not.** The save is deserialized first (`SandBoxGameManager.DoLoadingForGameManager` calls `Game.LoadSaveGame` for a loaded game), and then `Campaign.OnInitialize` runs with `_gameLoadingType == SavedCampaign` for the whole campaign graph. On that path it still performs the module fan-out `GameManager.InitializeGameStarter(CurrentGame, campaignGameStarter)` — `GameManager` here is the `GameType.GameManager` property (the live `SandBoxGameManager`), and `MBGameManager.InitializeGameStarter` loops `Module.CurrentModule.CollectSubModules()`, so the mod's `MBSubModuleBase.InitializeGameStarter` adds its `CampaignBehaviorBase` instances to `campaignGameStarter.CampaignBehaviors` exactly as on a new game. The SavedCampaign branch then replaces the deserialized manager's behavior list wholesale: `InitializeCampaignBehaviors(campaignGameStarter.CampaignBehaviors)`, `LoadBehaviorData()`, `RegisterEvents()` (the Q8 sequence). Templates are grafted the same way: `SandBoxManager.OnCampaignStart(..., isSavedCampaign)` → `SandBoxSubModule.RegisterSubModuleObjects` → `SandBoxManager.InitializeSandboxXMLs`, which runs `LoadXML("NPCCharacters")` on every campaign init — only `Heroes` is new-game-only — so the Q5 `ObjectManager` lookups of the mod's companion `CharacterObject`s work on an existing save.

**The save never contained behavior instances in the first place, so "the save predates the mod" is only a data question.** `CampaignBehaviorManager` persists exactly one field, `[SaveableField(1)] _campaignBehaviorDataStore`; the behavior list itself is not a saveable type field (the AutoGenerated definition collector only exposes the data store). The store maps behavior `StringId` → `BehaviorSaveData`, and the default `StringId` is the behavior's type name, `GetType().Name` — a mod should pin a stable id through the `CampaignBehaviorBase(string stringId)` constructor. Per save, the store is wiped and rewritten from the behaviors currently live (Q8's `OnBeforeSave` finding), so an old save simply has no record under the mod's key.

**What SyncData returns for missing data — two miss layers.** (1) No record for the whole behavior (the existing-save case): `CampaignBehaviorDataStore.LoadBehaviorData` tries `_behaviorDict.TryGetValue(stringId, ...)`, then a fallback that scans for any record whose key `Contains` the behavior's type name and re-keys it, and if that misses too it **never calls `SyncData` at all** — every field keeps its C# initializer value. A mod behavior therefore starts in its constructor-default state, which is the "no mod data yet" signal (e.g. a "spawned" flag initialized to false). (2) A record exists but one key is missing (a field a mod added in a later version): `BehaviorSaveData.SyncData<T>` does `_records.TryGetValue(key, out value)` — on a hit it assigns `(T)value` and returns `true`; on a miss it **returns `false` and leaves `ref data` untouched**, so `SyncData` implementations must branch on the return value wherever the default is not safe.

**Which of the Q8 events fire on this load: `OnGameLoadedEvent`, `OnSessionLaunchedEvent` and `OnAfterSessionLaunchedEvent` all fire; `OnNewGameCreatedEvent` does not.** In the SavedCampaign leg of `Campaign.DoLoadingForGameType` the order is `OnDataLoadFinished` → `GameManager.OnAfterGameLoaded` (module hook) → `Campaign.OnGameLoaded(starter)` (dispatches `OnGameEarlyLoadedEvent`, then `OnGameLoadedEvent`) → `Campaign.OnSessionStart(starter)` (dispatches `OnSessionLaunchedEvent` and `OnAfterSessionLaunchedEvent` back to back, then `ConversationManager.Build()` and `Settlement.OnSessionStart`). Afterwards, from `SandBoxGameManager.OnLoadFinished`'s `LoadingSavedGame` branch, comes `OnGameLoadFinishedEvent` (Q8: its only trigger). But `OnSessionLaunchedEvent`/`OnAfterSessionLaunchedEvent` fire identically on a new game — both loading branches call `OnSessionStart` — so they cannot distinguish "old save, spawn what is missing" from "new game, spawn everything" without extra state. The save file itself is stamped: `Campaign.DetermineSavedStats` appends an `Id:Version` snapshot of `ModuleHelper.GetActiveModules()` to the campaign's `_previouslyUsedModules` on both flows, and `MBSaveLoad` writes the active module ids into the save metadata (`metaData["Modules"]`).

**Hook to spawn missing companions: subscribe to `OnGameLoadFinishedEvent` (load side) alongside `OnNewGameCreatedEvent` (new game) — vanilla's own pairing (Q1/Q8) — and deduplicate by hero template.** `OnGameLoadFinishedEvent` is the only saved-load-only campaign event and it fires after every other load hook, after `OnDataLoadFinished` rebuilt the caches and after `OnSessionStart` finished settlements and conversations, so it is safe campaign state to create heroes in: scan the two lists vanilla itself scans on load, `Hero.AllAliveHeroes` plus `Hero.DeadOrDisabledHeroes`, compare `hero.Template.StringId` (`Hero.Template => CharacterObject.OriginalCharacter`) against every registered companion id from the Q4/Q5 registry, and for each miss create and place the hero with the exact Q1/Q3 mechanism (`HeroCreator.CreateSpecialHero` + `EnterSettlementAction.ApplyForCharacterOnly` into a town chosen by the Q3 predicate); placement bookkeeping is maintained by those actions live, so a late spawn needs no cache repair. Module-level hooks — `MBSubModuleBase.OnGameLoaded(Game, object)` or `AfterRegisterSubModuleObjects(bool isSavedCampaign)` (which does carry the saved-load flag) — are the wrong place: behaviors are not yet registered and the caches above have not run. One ordering fact matters for how "already exists" interacts with vanilla: `MbEvent.AddNonSerializedListener` prepends to a LIFO listener list, and since the mod's behaviors sit last in the starter list (vanilla's roster is added in `SandBoxManager.Initialize`, one call before the submodule fan-out in `Campaign.OnInitialize`), a mod handler on `OnGameLoadFinishedEvent` runs *before* vanilla's `CompanionsCampaignBehavior.OnGameLoadFinished` rebuild in the same event. That changes nothing about wanderer-count pollution though — spawned `Occupation.Wanderer` heroes join vanilla's counted set via `HeroCreated` regardless (Q1) — so keeping the count correct is a Q10 problem, not one to fix by choosing a different load hook.

**Orchestrator note (verified).** `CampaignBehaviorDataStore.LoadBehaviorData` (lines 86–105) calls `SyncData` only on an exact `StringId` hit or on the first stored key that `Contains` the behavior's type name; otherwise fields keep their initializers. ## Q10 — Harmony target for wanderer count

Status: VERIFIED

### Answer

**The patch target.** `CompanionsCampaignBehavior.AddToAliveCompanions(Hero companion, bool isTemplateControlled = false)`, in `TaleWorlds.CampaignSystem.dll`, namespace `TaleWorlds.CampaignSystem.CampaignBehaviors`. It is a **private instance method returning void**, so Harmony addresses it by name with an explicit parameter list — the optional `= false` is C# sugar and the runtime signature is `(Hero, bool)`. This is not counting logic inlined in a bigger method: the counter is the behavior's private `HashSet<CharacterObject> _aliveCompanionTemplates`, and the only `_aliveCompanionTemplates.Add` call in the whole extract sits inside this one method. The field has no accessor and appears in no other file in the extract, so there is no narrower or cleaner point — one prefix on the writer is the whole fix.

```
// patch 1 — the wanderer count (private instance, returns void)
private void AddToAliveCompanions(Hero companion, bool isTemplateControlled = false)
// patch 2 — vanilla hire option for mod heroes, decided in Q7 (private instance, returns bool)
private bool conversation_hero_hire_on_condition()
```

**Prefix, not postfix.** A prefix that returns `false` for a mod hero never enters the original, so the mod template simply does not go into the set and the patch never touches game state. A postfix runs after the `Add` has already happened, so it can only undo it: reach the private field through Harmony's field injection (`___aliveCompanionTemplates`) and remove the entry — a repair that duplicates the removal rule and is actively wrong when a mod hero shares a template with a real wanderer, because the set is keyed by template and shared: the postfix would drop a slot vanilla still needs. For a void mutator the exact semantics are skip-at-entry; undo-at-exit is a second copy of the logic that can corrupt state it does not own. Prefix also short-circuits the `IsTemplateKnown` scan of the whole template catalog, which the original would otherwise run for every mod hero.

**One prefix covers every path that could count a mod companion.** The callers are the creation event (`OnHeroCreated`, subscribed to `CampaignEvents.HeroCreated`), the saved-load rebuild (`OnGameLoadFinished`, which walks `Hero.AllAliveHeroes` and `Hero.DeadOrDisabledHeroes` filtered only by `IsAlive`/`IsWanderer`), the occupation-change handler (`OnHeroOccupationChanged`), and an unregistered duplicate of the load rebuild (`OnGameLoaded`). The creation path calls the writer with `isTemplateControlled: true`, which skips the `IsTemplateKnown` gate — that is why no data-only trick keeps mod heroes out of the count: whatever the template says (`is_template="false"`, a runtime-created character that is not in the catalog, a non-wanderer template), a live `Occupation.Wanderer` hero is counted at creation. Raising the mod heroes' occupation instead is out of scope: `IsWanderer` is what puts a hero in a tavern and moves it town to town (Q3) and what the hire conversation requires (Q6/Q7), and the SPEC wants those vanilla mechanics reused. Patching the callers is worse on every axis: three or four patches instead of one, each handler body also doing other work (the load pass loops both rosters; the occupation handler mirrors into `RemoveFromAliveCompanions`), so each would need a transpiler or a reimplementation — and a future caller added by the game would silently re-open the hole. Because the set is never saved (`SyncData` is empty) and is rebuilt through this same patched writer on every load, the exclusion is correct for new games, for existing saves and for every later session with no repair pass.

**What the exclusion buys, all at once.** With only vanilla templates in the set, every consumer of it sees a vanilla-only world: the spawn gate in `TrySpawnNewCompanion` (`_aliveCompanionTemplates.Count < _desiredTotalCompanionCount`), the per-category occupancy weighting in `GetCompanionTemplateTypeToSpawn` (per-category `Contains` count divided by that same target), the "not spawned yet" filter in `GetCompanionTemplateToSpawn`, and the cull pool in `TryKillCompanion`. The target itself is untouched, so the vanilla wanderer population stays exactly where the base game puts it.

**Yes — the same prefix keeps mod companions safe from the daily removal.** `TryKillCompanion` rolls 10% per day, draws a *template* at random from `_aliveCompanionTemplates`, then looks for the first alive hero with that `Template` and `IsWanderer` and removes it with `KillCharacterAction.ApplyByRemove` (only when unhired and not in the player's settlement). A template that never enters the set can never be drawn, so this path can never select a mod hero. No removal-side patch is needed: `RemoveFromAliveCompanions` is `Contains`-guarded, so the kill and occupation-change removals are no-ops for an uncounted hero, and `WeeklyTick`'s 40-day cleanup is hero-based and unaffected. Caveat, stated precisely: the protection is per *template*, not per hero. The hero search matches on template, so if a mod companion ever shared a template with a counted vanilla wanderer, the template would be in the set (added by the vanilla hero) and the mod hero could be the first match and be culled. The guarantee therefore depends on every mod companion owning its own template — the same unique-id requirement Q4/Q5/Q9 already rest on. Also deliberately untouched: `SwapCompanions`, so mod companions keep vanilla town-to-town movement.

**How the patch recognises a mod hero.** The set stores `companion.Template`, which is `CharacterObject.OriginalCharacter` (Q2), so the prefix inspects the very object the count keys on and compares its `StringId` (`MBObjectBase.StringId` — the `id` of a registered `CharacterObject`, which is what the mod's JSON ids become when its templates are registered) against the mod's registry of companion ids. That is the identical key the existing-save dedup uses (`Hero.Template.StringId`, Q9), so one Game-layer resolver answers both questions, and because it keys on the template object rather than on the unsaved set, it behaves the same before and after a save/load. `Hero.Template` is null when the hero's `CharacterObject` is itself the origin (`IsOriginalCharacter`), so the test must null-guard: exclude only when the template exists and its id is a registered mod id. A `CharacterObject` that is itself an origin and has a null/unknown id cannot be recognised this way — see Uncertain, which ties this to the open Q11 creation decision.

**How the second patch, already decided in Q7, is written.** Prefix on `LordConversationsCampaignBehavior.conversation_hero_hire_on_condition()` — same namespace, `private`, instance, no parameters, returns `bool`; it is the condition attached to the vanilla player line `main_option_faction_hire` (line 797), which is why priority and removal could not suppress it (Q7). The prefix applies the same registry test to `Hero.OneToOneConversationHero` and, for a mod hero, returns `false` with `__result = false`, so the vanilla hire option disappears while the mod's own hire line stays. Two patches total, one shared "is this hero one of mine?" predicate, both in the Game layer compiled against Lib.Harmony with the runtime supplied by Bannerlord.Harmony.

**Rejected alternatives.** (1) A postfix on the target property `_desiredTotalCompanionCount` — an expression-bodied `private float` property, so the patch would have to name the compiler-generated getter — inflates the goal instead of the tally: the same value bounds the new-game spawn loop in `OnNewGameCreated` (and indexing `list[i]` past the town list would throw), and it is the divisor of the category weights in `GetCompanionTemplateTypeToSpawn`, so the base game would spawn extra vanilla wanderers, in a distorted skill mix, for every mod companion; and it does nothing for `TryKillCompanion`, which still draws mod templates from the set and removes mod heroes. (2) A prefix on `TrySpawnNewCompanion` that fakes the count comparison — leaves the set polluted, so the cull still targets mod heroes, the category weights stay skewed, and the spawn body would have to be reimplemented. (3) Prefixing each caller (`OnHeroCreated`, `OnHeroOccupationChanged`, `OnGameLoadFinished`, `OnGameLoaded`) — skipping a caller wholesale skips vanilla work too, and any new caller in a later patch re-breaks the count. (4) Making the mod's heroes non-wanderers, or shipping templates the vanilla catalog will not accept — defeated by the `isTemplateControlled: true` bypass on the creation path and by the SPEC's requirement to reuse wanderer placement and hiring. (5) Patching `HashSet<CharacterObject>.Add` — a global patch on a BCL type, rejected outright.

**One residual interaction the patch cannot hide, and no other patch is proposed for it.** `TrySpawnNewCompanion` picks its town with a predicate that rejects any town whose `HeroesWithoutParty` holds an unhired `IsWanderer`. A mod companion standing unhired in a town therefore makes that town ineligible for the daily vanilla spawn even though it no longer occupies a counted slot — the count is corrected, the town choice is not. That is a one-per-day selection effect, not a count error, and it matches how the game already treats any hired-out or stuck wanderer; changing it would mean patching the spawn predicate too, which is out of SPEC scope ("vanilla wanderer behavior must otherwise be unchanged").
